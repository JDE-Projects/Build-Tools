# Screenshot capture

Repeatable README screenshots for the web tools, so the image in a repo is
regenerated by a command rather than captured by hand. Framing, window size and
theme come out identical every time, which means the picture only changes when
the design actually changes.

Two small scripts:

| Script | Job |
|---|---|
| `capture.mjs` | Drives headless Edge or Chrome, takes one PNG per shot |
| `compose.py` | Tiles those PNGs into the single image the README uses |

## Requirements

Nothing to install beyond what a dev machine already has:

- Edge or Chrome (found automatically on Windows and Linux)
- Node 22 or later (`fetch` and `WebSocket` are built in, so no npm packages)
- Python with Pillow, for `compose.py` only

## Using it

The app being photographed must already be running and serving a URL. Starting
it, and giving it something worth photographing, is the app's own business: see
"Fake data" below.

```bash
node capture.mjs shots.json
python compose.py ../screenshots/app-light-dark.png shots/dark.png shots/light.png
```

### Config file

```json
{
  "url": "http://127.0.0.1:3123/",
  "width": 900,
  "height": 648,
  "outDir": "shots",
  "waitFor": "document.querySelector('.device-card')",
  "setup": "selectDevice(document.querySelector('.device-card').dataset.id)",
  "waitForData": "document.querySelector('#cpu-percent').textContent.trim()",
  "shots": [
    { "name": "dark",  "script": "applyTheme('dark')"  },
    { "name": "light", "script": "applyTheme('light')" }
  ]
}
```

| Key | Required | Meaning |
|---|---|---|
| `url` | yes | Address of the already-running app |
| `shots` | yes | One entry per image, with keys `name` (becomes the filename), `script` (JavaScript run in the page before the shot) and an optional `settleMs` overriding the top-level one |
| `width` / `height` | no | Viewport size, default 1280x800. Pinned via the browser's device metrics, so the result does not depend on the display |
| `outDir` | no | Where the per-shot PNGs go, relative to the config file. Default `shots` |
| `settleMs` | no | Pause after each shot's script before capturing, default 400. A shot can override it |
| `scale` | no | Pixel density, default 1. Use 2 for a high-resolution image |
| `waitFor` | no | JavaScript polled until truthy, before `setup` runs. Use it to wait for the page to be usable |
| `setup` | no | JavaScript run once after `waitFor`, before any shot |
| `waitForData` | no | JavaScript polled until truthy, after `setup`. Use it to wait for live data to arrive, so shots are never of an empty panel |
| `timeoutMs` | no | Limit for every wait, default 30000 |
| `browser` | no | Full path to Edge or Chrome, when it is somewhere unusual |

Both scripts stop with a message and a non-zero exit code on any problem: a
missing browser, a wait that never came true, JavaScript that threw, or images
that do not match in size. Nothing is composed from a partial run, so a broken
capture cannot quietly produce a wrong README image.

## Fake data

Screenshots of an empty app are useless, and screenshots of a real network are
a privacy leak: real hostnames, real addresses. So an app supplies its own
invented data rather than being photographed against a live install.

The pattern that works without adding a demo mode to the app itself:

1. Start a small throwaway server that returns canned readings.
2. Write a temporary config or data file pointing the app at it.
3. Run the app from a temporary copy, on a spare port, so nothing touches the
   real working copy or its saved data.
4. Capture, compose, then delete the temporary copy.

The app runs completely unmodified and unaware. See
`tools/screenshot/` in Simple Network Dashboard for a worked example.
